# 中文架构 Skill 编写规范

本文件是维护规范，不是又一个 Skill；各运行入口分别保持自包含。新增或修改 Skill 时读取本规范，执行范围遵循用户请求与项目适用规则。

## 目录与元数据

在 `.agents/skills/<name>/SKILL.md` 创建入口，name 使用小写英文 kebab-case，与目录一致；正文和 description 使用中文，保留准确技术标识。YAML 必须有非空 name、description，description 说明做什么、何时触发以及必要边界，避免“所有开发都加载”。本体系只使用这两个通用字段，不引入 Codex 专用 UI 配置。

技能按后端、前端、数据库、API 领域划分；语言、框架、产品放在该 Skill 的 references 内。根目录下不放 README.md 等平铺说明，避免被 DSH 误作 Skill 入口。维护文档放在本目录。

## 入口结构

入口应包含：任务范围、先读哪些项目事实、按需引用路由、执行步骤、跨领域协作条件和交付要求。入口只保留关键规则，目标控制在约 100 行以内（维护建议，不是 DSH 限制）。references 用相对 Markdown 链接并写明何时读取；不一次读取所有语言/框架。

common.md 是语言无关基础指南；已有完整专题的语言可直接路由到专题，不要求先读摘要再读展开内容。语言专属规则仅由对应专题定义。跨领域规范由职责所属 Skill 维护；明确请求加载，不假定 DSH 支持自动依赖/继承。避免循环要求和跨 Skill 必读链。

## 规则强度

区分项目既定约定、正确性约束和默认建议。举例：资源授权/参数绑定属于正确性要求；是否 DDD、分微服务、每类一个接口不是普适要求。既有约定与建议冲突时说明取舍，不借 Skill 擅自扩展改动范围。涉及真实矛盾或缺少关键需求再询问用户。

不要强制升级框架、运行生产迁移、安装工具或重构全仓库。版本敏感 API/插件配置以项目锁定版本和官方资料为准；不把未经验证的细节写成保证。

## 扩展与验收

新增语言/框架前先有实际适用场景；创建有内容的指南，更新入口链接，不提交空目录或 TODO 占位。每份参考应有唯一职责和可观察的验收点。

检查 YAML、名称唯一性、相对链接、孤立引用与未完成占位符。使用 DSH 本地文件提供器检查发现和正文加载；静态校验不等于模型行为测试或 UI 验证。选取一个正向任务、一个应由其他 Skill 处理的任务和一个跨领域任务，核对路由及读取范围。

本次路由验收示例：Java 持久化→backend 编码基线+Repository/MyBatis-Plus 专题，不读取 Go；React 搜索竞态→frontend/state；增加唯一约束→database；修改分页错误响应→api；新建订单接口→api 与 backend，发生表变更时才加载 database。

## 规范强度与变更维护

MUST/MUST NOT：必须/禁止，表明正确性或明确选定的架构约束。SHOULD：默认推荐，偏离时说明场景与理由。MAY：按需采用，不为了“完整”强制增加抽象。

新增模块使用明确选定的基线；维护旧模块优先兼容，不能把规范升级等同于全仓重构。修订时同步入口路由、示例及使用说明；对架构基线的改变记录理由和迁移影响，不静默替换已讨论的设计。

本次 Java 基线还原为业务模块 api/internal、internal/web、简单 AppService、复杂后按用例/能力分包、Req/Resp/DO、语义相同 DTO 可复用、模块所有权和字符串业务码。各语言的目录形式无需完全相同，通用原则与语言实现保持分层。

## 入口与单一权威定义

多语言入口按语言分节，标明成熟度；用任务表选择参考，不把一种语言所有路由塞进长行。基线保持短小，专题按变化加载，链接不等于全量递归读取。

同一规则仅在职责所属文档定义，入口做导航，验证指南只描述证据。后端 Java 的格式/参数归 coding-style，模型/构建归 data-objects，类型选择归 record-vs-class，持久化边界归 repositories-and-modules，跨模块访问边界归 api-layout，方向与调用归 integrations，输入存在性与绑定归 input-contracts。检查清单不另增例外。

使用代表任务观察实际产物与范围，包括小修改是否被无谓扩写；静态路由检查、作者自行试用、独立模型评测和框架集成测试分开报告，不能相互冒充。
