# 分支与提交规范（团队共识）

项目已有分支约定时以项目约定为准。

## 分支管理

采用简化 trunk-based + 任务分支沙箱（SHOULD）：

1. `main` 始终保持可用：可用性门禁放在**合入前**——合入前 MUST 确认构建/测试通过（或说明无法验证的原因）；任务分支上的中间提交不要求每次可用。
2. 一任务一分支：功能开发从 `main` 拉分支，命名 `feat/<简短主题>`；修复用 `fix/<问题>`；实验性探索用 `try/<主题>`（可不合入）。不推送 remote 的本地分支是私有沙箱（推送授权见安全边界）。
3. 分支生命周期尽量短（SHOULD，一两天内量级）；无法及时合入的长命分支 SHOULD 在每天或每次继续任务时同步 `main`（未推送的本地分支用 rebase，已共享分支用 merge），不让冲突积累；开启 `git rerere` 复用重复的冲突解决。
4. 同一台机器上的并行任务用 `git worktree` 隔离（一任务一分支一 worktree）；worktree 是一次性资源，合入后删除并 `git worktree prune`。
5. 直接在 `main` 上提交仅限微小改动（typo、文档修正）；其余情况 SHOULD 走分支。
6. 分支合并后删除；不合入的探索分支注明原因后删除。

## 提交信息格式

```text
<type>(<scope>): <中文描述>

<可选正文>
```

### Type

- `feat`：新增能力
- `fix`：修复问题
- `refactor`：重构
- `docs`：文档
- `test`：测试
- `chore`：工程维护
- `perf`：性能
- `ci`：持续集成

`scope` 标识改动所属模块，可用时 SHOULD 提供（如 `docs(aes): …`）。

### 提交正文

1. 提交正文应尽量紧凑：
   - 只有一个整体说明时，使用一个自然段。
   - 有多个独立改动点时，在同一个正文中使用无序列表；列表项之间不要插入空行。
   - 不要把每个小点都拆成独立段落；多个 `-m` 参数只用于确实需要分隔的正文段落。

2. 推荐使用多个 `-m` 参数表达标题和正文：

```bash
git commit -m "docs(aes): 新增编排与状态设计文档" \
  -m $'- 拆分编排引擎、DSL 与 GraphArtifact 设计\n- 补充状态分层与恢复机制说明'
```

如果正文是一段完整摘要，也可以直接写成：

```bash
git commit -m "fix(aes): 修正 thread 恢复判断" \
  -m "修正重连后未按原 graph_artifact_key 恢复兼容版本的问题。"
```

不要在普通双引号中写 `\n` 期待它变成换行；普通双引号会把它作为字面量传给 Git。不添加 AI attribution 署名。

### 提交粒度

任务分支上允许 **checkpoint 式推进提交**（记录任务当前进展的 WIP 提交，描述本步做了什么），但 MUST NOT 混入与该任务无关的改动；不提交与摘要无关的文件（如本地调试产物、IDE 配置）。合入前 SHOULD 视需要整理提交历史（squash/fixup 或保留，由用户在合入时决定）。直提 `main` 的提交仍保持一次提交一个主题、可独立回退。

## 安全边界

- **提交授权分两级**：任务分支上的 checkpoint 式推进提交，在任务开始时（开分支/明确开工时）一次性征得用户同意后免逐次确认，偏离既定主题的改动除外；直提 `main`、合入分支、整理历史（squash/fixup）等其他提交仍需逐次以文本询问"是否提交"并附建议提交信息，不用选项组件强制选择。未获授权不提交。
- **推送必须显式授权**：`git push`（含 tag 推送）仅在用户明确要求推送（"推送"/"push"等）时执行；"提交"指令默认不含推送，MUST NOT 链式执行。
- 不自动执行合并分支、打 tag，除非用户明确要求。
- 不使用 `git push --force` 覆盖共享分支。
- 提交前检查敏感文件、`git diff --check` 和与改动范围匹配的验证命令；MUST NOT 带着已知失败提交并谎称通过。
