# 分支与提交规范（团队共识）

项目已有分支约定时以项目约定为准。

## 分支管理

采用简化 trunk-based（SHOULD）：

1. `main` 始终保持可用：合入前 MUST 确认构建/测试通过（或说明无法验证的原因）。
2. 功能开发从 `main` 拉分支，命名 `feat/<简短主题>`；修复用 `fix/<问题>`；实验性探索用 `try/<主题>`（可不合入）。
3. 分支生命周期尽量短（SHOULD，一两天内量级）；长期分支定期同步 `main`。
4. 直接在 `main` 上提交仅限微小改动（typo、文档修正）；其余情况 SHOULD 走分支。
5. 分支合并后删除；不合入的探索分支注明原因后删除。

## 提交信息格式

```text
<type>(<scope>): <中文描述>

<可选正文>
```

### Type

- `feat`：新增能力
- `fix`：修复问题
- `refactor`：重构
- `docs`：文档
- `test`：测试
- `chore`：工程维护
- `perf`：性能
- `ci`：持续集成

`scope` 标识改动所属模块，可用时 SHOULD 提供（如 `docs(aes): …`）。

### 提交正文

1. 提交正文应尽量紧凑：
   - 只有一个整体说明时，使用一个自然段。
   - 有多个独立改动点时，在同一个正文中使用无序列表；列表项之间不要插入空行。
   - 不要把每个小点都拆成独立段落；多个 `-m` 参数只用于确实需要分隔的正文段落。

2. 推荐使用多个 `-m` 参数表达标题和正文：

```bash
git commit -m "docs(aes): 新增编排与状态设计文档" \
  -m $'- 拆分编排引擎、DSL 与 GraphArtifact 设计\n- 补充状态分层与恢复机制说明'
```

如果正文是一段完整摘要，也可以直接写成：

```bash
git commit -m "fix(aes): 修正 thread 恢复判断" \
  -m "修正重连后未按原 graph_artifact_key 恢复兼容版本的问题。"
```

不要在普通双引号中写 `\n` 期待它变成换行；普通双引号会把它作为字面量传给 Git。不添加 AI attribution 署名。

### 提交粒度

一次提交一个主题（MUST NOT 混合无关改动）；同一任务的关联变更一起提交，保持每个提交可独立回退。不提交与摘要无关的文件（如本地调试产物、IDE 配置）。

## 安全边界

- 不自动执行 `git commit`；建议提交时询问用户，选项显式区分「仅提交」与「提交并推送」，不得只有合并选项。
- **提交与推送是两个独立授权阶段：用户批准提交不代表批准推送**。`git push`（含 tag 推送）必须用户单独显式授权；严禁在用户仅答复提交时链式执行 push。
- 询问未获答复（被关闭/跳过）时视为未授权：不提交也不推送，以文本再次确认。
- 不自动执行合并分支、打 tag，除非用户明确要求。
- 不使用 `git push --force` 覆盖共享分支。
- 提交前检查敏感文件、`git diff --check` 和与改动范围匹配的验证命令；MUST NOT 带着已知失败提交并谎称通过。
