# yak CLI：通过 CLI 把 kit 应用到各 vibe coding 工具

> 状态：implemented ｜ 提出于 2026-11-19

## 背景

kit 需要发布到 npm 并支持多工具安装。最初讨论过"每个 DSH 插件发一个包"，后来明确真正的需求是**自己的 CLI**：`yushe-agent-kit` 作为单一 npm 包发布，CLI 是入口，`.agents/` 资源（skills/rules/插件）是载荷，由 CLI 映射安装到各工具。

## 决策

1. **单包 + CLI 入口**：根 package.json（bin: yak / yushe-agent-kit），资源不独立发包；`npx yushe-agent-kit install <target>` 是标准用法。
2. **registry 即映射权威**：`src/cli/targets/registry.js` 是"资源 → 各工具目标路径"的唯一权威（此前 AGENTS.md 预留的"安装映射"节的落地）；**未核实目录约定的目标（opencode/codex/gemini）拒绝安装**，不凭印象写路径。
3. **软链优先、复制兜底**：软链更新源即生效；实体目录（用户自有安装）判为 conflict 不覆盖。
4. **依赖边界按载荷区分**：`.agents/dsh/plugins/*` 保持零依赖纯 ESM（`link:` 安装不会安装依赖，这是插件的硬约束）；CLI 是常规 npm 包，TypeScript 编写、构建产物（dist/）分发，可自由使用运行时依赖（commander）。早期版本把插件的零依赖约束错误地推广到了 CLI，已纠正。
5. **doctor 是杀手级功能**：诊断同名遮蔽（项目 `.dsh/skills` 优先于 `.agents/skills`）、双源实体目录、失效软链、SKILL.md 命名不一致——都是实际踩过的坑。
6. 技术选型 Node 而非 Go：资源与 CLI 同包发布是单包方案的前提。

## 放弃的替代方案

- 每个 DSH 插件独立发包：多一次管理，kit 定位是配套整体，版本耦合反而是优点。
- 根 package.json 声明 dsh.bundle.patch 让 `dsh plugin add yushe-agent-kit` 直接装：有了 CLI 后不需要，插件保持包内子目录由 CLI 安装。
