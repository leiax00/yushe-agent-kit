# 分支与提交规范（团队共识）

触发场景：创建/切换/合并分支、编写提交信息、整理提交历史。项目已有分支约定时以项目约定为准。

## 分支管理

采用简化 trunk-based（SHOULD）：

1. `main` 始终保持可用：合入前 MUST 确认构建/测试通过（或说明无法验证的原因）。
2. 功能开发从 `main` 拉分支，命名 `feat/<简短主题>`；修复用 `fix/<问题>`；实验性探索用 `try/<主题>`（可不合入）。
3. 分支生命周期尽量短（SHOULD，一两天内量级）；长期分支定期同步 `main`。
4. 直接在 `main` 上提交仅限微小改动（typo、文档修正）；其余情况 SHOULD 走分支。
5. 分支合并后删除；不合入的探索分支注明原因后删除。

## 提交信息

格式（团队共识）：

```
<type>: <简洁英文摘要>

[可选正文：动机与影响，中文]
```

1. 摘要行使用简洁英文祈使句，不超过 50 字符（SHOULD）；正文用中文说明为什么改、影响面。
2. type 取值：`feat` 新功能 / `fix` 修复 / `refactor` 重构（不改行为）/ `docs` 仅文档 / `test` 仅测试 / `chore` 构建、工具、依赖等杂项。
3. 一次提交一个主题（MUST NOT 混合无关改动）；同一任务的关联变更一起提交，保持每个提交可独立回退。
4. 提交前检查暂存内容与摘要一致；不提交与摘要无关的文件（如本地调试产物、IDE 配置）。
5. 提交前运行适用的检查；失败时先修复或拆分提交，MUST NOT 带着已知失败提交并谎称通过。

## 敏感操作

强推（force push）、改写已共享分支的历史、操作他人分支前 MUST 获得用户明确同意。
