# 数据模型与约束

先列业务实体、关系、生命周期、访问模式与数据归属。默认采用能表达业务不变量的关系模型；冗余字段需说明更新来源与一致性策略，JSON 列不替代需要约束和高频查询的结构字段。

沿用现有命名，缺少约定时使用一致的 snake_case。主键选择考虑生成位置、索引局部性和暴露风险；主键与业务唯一键分离。金额用精确数值类型并约定币种和精度，时间明确是否表示时间点。不要用空字符串、0 和 NULL 混合表示缺失。

在数据库能够约束的范围使用 NOT NULL、唯一键、外键和 CHECK；产品和版本是否实际执行约束需验证。外键是否启用由部署与完整性策略决定，不因“企业级”一律禁用；不用外键时明确补偿校验与孤儿记录处理。

新业务状态默认存储显式稳定字符串业务码并定义转换，不依赖枚举序号或 Java 常量名称。业务 code 与等级 level 分离；已有数字协议、位掩码或有证据的容量约束可采用明确数字码。默认评估 VARCHAR 而非原生 ENUM 以利演进，长度、合法值约束及已有兼容性按实际需求决定。租户隔离需覆盖查询与唯一键，例如租户内唯一的业务编号应含 tenant_id；不能仅依赖应用查询条件。

逻辑删除按恢复、审计和保留策略决定，非所有表必备。需重复复用业务键时设计活跃行唯一性；unique(key, deleted) 无法简单支持无限次删除重建。审计字段不等于完整审计日志，个人数据删除也不等于逻辑删除。

索引、分区、归档和冷热拆分由规模与查询证据驱动，避免预先为所有表分库分表。
