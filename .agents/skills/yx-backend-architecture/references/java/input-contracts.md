# 输入契约、可信范围与模型绑定

## 请求意图与可信上下文

客户端 DTO 仅表示请求意图。认证主体、有效租户、权限与数据范围由服务端可信来源构造，不能作为客户端可绑定字段混入同一个 Query/Command。用例可把已验证的请求意图与可信范围组合成内部查询条件，条件类型不接受 HTTP 自动绑定。

如果授权规则把“操作”与“资源范围”配对，必须保持配对关系；不能把多条授权中的操作与范围分别求并集后任意组合。无真实身份接入时不为跑通流程新增匿名白名单或自报特权头；测试替身只用于明确的测试环境。

MUST 在资源查询、修改、批量操作和自定义 SQL 中保持有效范围；只按 ID 查到对象不等于获得访问权限。身份校验、资源授权和数据过滤各自承担职责，不用其中一个替代全部。

## 缺失、显式 null 与默认值

每个输入契约明确区分：字段未提供、显式 null、空字符串、空集合和合法值。Create、全量替换、PATCH 的含义不同，不能共用一个万能 save DTO 掩盖差异。

PATCH 常见语义是“未提供不修改、null 清空或拒绝、值为替换”；只有当前契约确实采用时执行，不擅自套用。需要区分未传时，primitive 的 0/false 往往不足；包装类型可区分 null 与数值，但本身不能区分 JSON 字段缺失与显式 null，必须有实际支持的存在性表示或绑定策略。

默认值不能在绑定/构造阶段提前抹掉业务需要区分的状态。先确定请求契约，再决定规范化和校验顺序；长度、空白、重复项和集合 null 元素都需定义。禁止把显式非法值“修正”为默认成功值。

## 绑定路径与存在性

如果项目依赖无参构造 + setter 绑定表达“缺省保留默认、显式 null 拒绝”，优先保留验证过的 class 方案，不能无测试替换为 record。

不能普遍声称 record 永远无法表达字段存在性，也不能声称 class 自动解决 null 契约。creator/setter、注解、Jackson 模块及版本可能影响行为，必须用实际绑定链路验证“缺失/null/有效值/非法值”四类输入。真实问题需要存在性模型时使用受支持的类型或绑定方案；不要为规避绑定随意引入通用 JSON 解析框架。

固定结构请求使用类型化 DTO 和项目支持的 Bean Validation，不默认改用 Map/JsonNode 手写逐字段解析。只有真实动态结构或现有协议需要时采用树模型，并仍验证约束。

## GET、分页与返回契约

GET 筛选可用受支持的请求对象绑定，保持现有 URL 参数名、日期格式、多值语义和分页约定，不为减少 Controller 参数改成 GET JSON body。不能把服务端租户/授权范围混入请求绑定对象。

复用已有公共分页输入/结果，业务条目仍使用自己的模型；公共模型不依赖 ORM/Servlet，框架 Page/IPage 转换留在适配边界。不因引入框架改变外部页码起点、大小限制和排序。

已有统一响应时由 Web 层负责协议包装，应用层返回业务结果。验证正常响应、字段错误、异常处理、认证/授权拒绝和默认错误入口的实际形状；204、文件与流不强行包装 JSON。新增响应外壳属于契约变更，需要同步文档和消费者，不能作为随手“统一风格”的修改。

## 验证

覆盖缺失/null/空值、未知字段策略、类型错误、整数边界、布尔属性命名、集合重复项、规范化前后长度和实际 JSON 字段。未知字段是否拒绝沿用明确契约，不因复用旧项目规范突然收紧已有 API。

请求模型变更除编译外还应验证实际序列化/反序列化。Mock 或对象手工构造不能证明 HTTP 绑定行为。
