# 业务日志与审计

## 日志服务于排查

在关键变更、外部调用、批处理和有诊断价值的拒绝点记录有界信息，不给每个方法机械增加进入/退出日志，也不以万能切面替代业务语义。

优先使用现有 SLF4J 占位符和日志设施，记录操作、资源标识、数量、修改字段标志以及可信身份范围。复用 requestId/traceId；需核实实际日志配置输出关联标识，异步任务的上下文传递与清理不能假定自动生效。

成功写入阶段信息通常 INFO，普通查询摘要通常 DEBUG，预期拒绝按排查价值选择 DEBUG/WARN，未知故障在统一异常边界 ERROR 并保留堆栈。等级按项目运营约定调整；避免逐层 catch-log-rethrow 重复打印。

禁止无差别打印 DTO、响应、完整集合、SQL 参数、自由文本、凭据或令牌。对外部可控日志内容限制长度并处理换行等日志注入风险；标识也按实际敏感等级脱敏，不把“数字 ID”视作天然公开。

## 事务结果不能提前宣布

@Transactional 方法体结束并不代表事务一定提交；可能仍处于代理提交阶段或外层事务中。提交前日志只能描述处理阶段，不写确定的“提交成功”。确需记录提交结果时使用项目已有事务完成机制，并验证失败/回滚；不为增加一条日志引入通用事务包装层。

异常路径保留真实失败，不能为日志改变返回值、异常类型、权限或回滚行为。事务完成后发布一次事件也不自动成为可靠审计交付。

## 诊断日志与操作审计不同

诊断日志不能替代需要可靠保存的操作审计。已有统一审计能力优先复用，不为每个模块重复建立同构操作日志表；确有独立业务语义的状态历史、版本记录仍由所属业务维护。

通用记录契约、脱敏与基础设施可复用；存储适配、业务详情和保留要求按实际需求决定。不将统一审计解读为必须一张全局表或必须新增独立服务。

明确成功/失败审计与业务事务的关系、故障影响、幂等及可靠交付要求。不能把异步告警当可靠留痕，也不能为保留失败审计随意用 REQUIRES_NEW 拆断业务一致性。

## 按风险验证

修改日志/审计时验证关键节点覆盖、敏感字段排除、级别、关联标识及回滚不误报；需可靠审计时再验证存储/投递失败路径。纯格式修改不强制增加全套日志测试。
