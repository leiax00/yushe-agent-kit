# 服务部署型发版（发服务而非发包）

仓库的交付物是**可部署的服务**（镜像 / 制品 + 部署流水线），不是发到包管理器的库。微服务独立部署的单仓是典型形态：每服务一条版本线、按服务发版。

## 分工

- 版本**落位**（载体与升版命令）仍按 SKILL.md 技术栈路由的参考执行，本参考不改写。
- 本参考负责**发布形态特化**：版本线、tag、渠道与记录在"发服务"下的约定。

## 版本线

- 每服务一条 independent 版本线（策略判定见[版本决策](version.md)中"微服务独立部署的单仓"）。
- 版本载体：服务目录内有 `pom.xml` / `package.json` / `pyproject.toml` 时按技术栈参考升版；无载体（纯 tag 流）时以 git tag 为唯一版本事实，不强行造版本文件。

## tag 与发版粒度

- per-service tag 前缀：`<服务>/vX.Y.Z`；一个服务一次发版一个 tag，不打仓库级 mono-tag。
- 本次发哪些服务由变化驱动：`git diff --name-only <服务上个tag>..HEAD -- <服务目录>` 非空即候选；无变化的服务不发，不空转版本号。
- 跨服务接口变更时先确认消费方的兼容窗口，必要时同批发版。

## 渠道发布

- 渠道 = 构建与部署流水线，不是 npm / PyPI / Maven 仓库；镜像 tag 与 git tag 同源（如 `svc-a:1.2.3`），tag 推送即触发（或按仓库 CI 约定手动触发）。
- 环境推进（staging → prod）与发布批次按仓库流水线约定；本 skill 只管"版本与 tag 正确就位"。
- 回滚 = 重新部署旧 tag / 旧镜像，不是版本回退，更不删 tag。

## 记录

- 变化记录按服务拆分：`releases/<服务>/unreleased.md`，发版时迁入该服务自己的版本文件（布局权威在 yx-docs）。

## 边界

- 同仓混合"发库 + 发服务"（平台库 + 微服务）时：库走技术栈参考的包渠道，服务走本参考，版本线各自独立。
