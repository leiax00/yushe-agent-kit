# 发布操作

版本已定后的执行清单：前置检查 → 记录迁移 → 版本落位 → 提交 → tag → 渠道发布 → 汇报。步骤本身工具中立；**版本落位与渠道发布的具体命令按 SKILL.md 的技术栈路由加载对应参考**执行。

## 清单

1. **前置检查**：在 main 上；工作区干净；与远端同步（领先时先推送、落后时先 `git pull --ff-only`）；构建与测试通过（门禁命令按项目惯例，参考文件里只补充版本落位特有的验证）。
2. **记录迁移**：`docs/releases/unreleased.md` 的内容迁入 `docs/releases/vX.Y.Z.md`（含日期与版本标题；格式权威在 yx-docs 发版参考）；unreleased.md 重置为空模板，下个版本继续累积。
3. **版本落位**：按技术栈参考执行——探测版本唯一事实来源、一条命令统一升版（不逐文件手改）、跑该参考要求的完整性验证（lock 同步 / reactor 编译等）。Go 仓库例外：无版本文件，本步骤并入第 5 步的 tag。
4. **提交**：版本号 + 记录迁移一个提交：`chore(release): 发布 vX.Y.Z`（直提 main 的一主题提交，按 git 工作流规则逐次确认）。
5. **推送与 tag**：提交推送、`git tag vX.Y.Z` 及 tag 推送均 MUST 用户显式授权，逐项执行不打包；tag 名与记录文件名、版本载体三者同源。
6. **渠道发布**：命令按技术栈参考执行（npm / mvn deploy / uv publish / 推 tag 即发布）；同样 MUST 显式授权；发布后按参考给的核验方式确认就位。
7. **汇报**：版本号、tag、发布渠道与验证结果；漏发 / 失败如实报告并给出补救路径（deprecate、yank、补 patch 等，见各技术栈参考），不粉饰。

## 边界

- 发版不引入分支：全部动作发生在 main；发版中途失败（如 publish 网络错误）时记录做到哪一步，重试从断点继续，不重复已成功的步骤。
- 多包仓库：先按[版本决策](version.md)的策略判定确定单线 / 多线，再执行本清单——
  - 统一版本：一份 unreleased 与一个版本号，清单走一遍即可；tag 用仓库号（mono-tag）。
  - 独立版本：变化记录按线拆分（`releases/<线名>/unreleased.md` 或 changesets 变更集，布局权威在 yx-docs）；本次要发的线各走一遍清单，发版日期各线独立；tag 用 per-package / per-service 前缀（`pkg-a/v1.2.3`）。
  - 依赖传播：被依赖包升级后，依赖方版本引用的跟随方式（workspace 协议 / Maven BOM pin / go.mod replace）按技术栈参考与仓库既有约定处理；依赖 bump 是否构成依赖方的一次发布由仓库策略定，changesets 仓库跟随其输出。
