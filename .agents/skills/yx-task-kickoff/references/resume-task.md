# 继续一个已有任务

会话开始或中途接手一个进行中的任务分支时的恢复流程：识别现场 → 同步 main → 恢复计划。与"开始新任务"的区别是多了一个**归属与漂移检查**。

## 第 0 步：识别现场

- 当前分支与所在 worktree：`git branch --show-current`、`git worktree list`；工作区状态 `git status --short`。
- 有未提交改动：先判断属于哪个任务（结合最近提交与对话主题），再决定继续或询问去向。
- 分支归属不明（既不是本会话开的，也没有对应 note/todo）时向用户确认，不默认接管。

## 第 1 步：同步 main（漂移检查）

- `git fetch origin` 后比较 `main..HEAD` 与 `HEAD..main`：落后量小（几个提交/一天内）可先继续；落后明显或触碰了相同文件时，**先同步再继续做**——冲突越晚解越贵。
- 未推送的本地分支用 `git rebase main`；有冲突逐个解决后继续，重复出现的冲突依赖已开启的 `git rerere` 自动复用。
- rebase 后跑与改动范围匹配的验证，确认任务没有被 main 上的变化破坏（语义冲突比文本冲突更隐蔽）。

## 第 2 步：恢复上下文与计划

- 读该分支的最近提交和对应 note（如有），用一两句话复述任务目标与剩余步骤，继续推进。
- 发现任务已失去前提（main 已实现同类改动、需求取消）时向用户确认是否废弃，不合入的分支注明原因后删除。

## 合不进去的对策

因工程原因（等评审、等联调）无法及时合入时，按优先级：

1. 拆增量：把分支中可独立成立的部分先合回 main，剩余部分继续。
2. 能藏就能 flag：未完成的功能用开关隐藏后先合代码。
3. 不兼容升级用 expand-contract：先合"新旧并存"，迁移完再合"删旧"；确实无法共存的破坏性改动，把不可共存的那一步压到最薄，必要时配相关模块的短期冻结。
