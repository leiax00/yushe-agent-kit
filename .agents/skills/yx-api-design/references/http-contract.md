# HTTP 契约规范

## 资源与方法

沿用项目资源命名和版本策略。GET 用于读取且不触发业务写操作；POST 创建或执行业务命令；PUT 与 PATCH 的替换/部分修改语义需明确。复杂业务动作可显式建模如取消订单，不必为了 CRUD 风格暴露任意状态修改。

使用合适 HTTP 状态：成功创建可返回 201 和资源位置，异步受理用 202 并提供状态查询语义；无响应体的 204 不再附 JSON。认证失败、无权访问、不存在、状态冲突与参数错误分别表达，沿用项目的 400/422 策略。不能把所有错误都包装为 HTTP 200。

## 字段与输入

区分字段省略、null、空字符串、空数组。标明必填、长度、数值范围、格式和未知字段处理。金额、大整数、日期/时间精度与时区在客户端之间一致，必要时用字符串表达精确值。请求 DTO 使用字段白名单，禁止绑定内部 entity。

身份与 tenant 不直接信任客户端字段。查询、下载、批量接口也需资源级授权。对允许的筛选和排序字段建立白名单，限制 pageSize、批量数量和请求体大小。

## 列表

数据量较小且需要跳页时可用页码分页；明确从 0 还是 1 开始、页大小上限以及 total 是否存在/精确。大数据或持续变化列表评估游标分页，定义稳定排序和唯一 tie-breaker；游标应绑定筛选/排序和访问范围，不能作为授权凭证。

## 错误

使用稳定机器可读错误码、人类可读说明及请求追踪标识；字段错误可带字段路径。错误文案不是客户端分支条件——分支判断用 `code`，展示文案由客户端决定。可沿用已有错误封装或 Problem Details 风格，但不为采用新格式强改已发布接口。不要返回堆栈、SQL、密钥或可用于枚举敏感资源的信息。

**国际化渲染**（面向多语言客户端 SHOULD；单语言项目可暂缓，结构先留余地）：

- `code` 兼作客户端 i18n 资源键；`message` 是默认语言的兜底文案与调试信息，i18n 客户端不直接展示。
- 带参数的错误用结构化参数承载，默认**命名参数**——翻译中语序会变，位置参数易插错；项目既有位置参数约定沿用并在契约中标注顺序含义。
- 参数值不得是已渲染句子（会把语言锁死在服务端）；数字、标识符、枚举名优先，由客户端按 locale 格式化（含复数规则）。
- 客户端兜底链：本地无该 code 的资源 → 展示 `message`（默认语言）→ 展示 `code`；未知 code 不崩溃。
- `code` 与参数名是公共契约：发布后不改语义、不复用；错误目录（code → 参数 schema）由服务端与客户端共享一份维护，不各写一份漂移。

示例（字段名按项目契约调整）：

```json
{"code":"ORDER_QTY_EXCEEDS_MAX","message":"数量超过上限","args":{"max":99},"requestId":"req-example"}
```

服务端权限校验为权威依据；是否对不存在和无权限统一返回 404 由资源泄露策略决定。

## 契约载体（OpenAPI）

- HTTP API 的 schema SHOULD 以 OpenAPI 源文件记录（YAML 优先），不依赖口头约定或散落的接口文档。
- 源文件唯一：改契约 MUST 同步更新 OpenAPI 源；生成与手写双轨并存时明确哪边是权威，只保持一个权威方向。
- 无既有载体时默认手写源文件（design-first，契约评审先于实现）；采用注解生成时，生成产物是提交还是 CI 产出由项目定，同样只有一个权威。
- 文件位置与跨服务发现遵循 yx-docs 的 API 契约布局（单服务 `docs/apis/`，monorepo `docs/services/<服务>/apis/`，文件名即服务名）；spec 的破坏性变更 MUST 同步记入该服务 `releases/unreleased.md`。
- 错误结构登记为可复用 schema（`components/responses` 或等价机制，含 `code`/`args`/`requestId`）；code 清单以错误目录为权威，OpenAPI 不重复枚举（或由目录生成），避免两处漂移。

## Java 模块 API 与 HTTP API

Java 的 api 包是同 JVM 公开模块契约，HTTP Controller 位于模块 internal/web；跨服务通信仍以 HTTP/RPC/消息协议为边界。外部状态码默认使用显式稳定字符串业务码，不暴露 Java ordinal/name；定义未知枚举值处理策略。具体 Java Port/Adapter 与 DTO 归属由 yx-backend-architecture 负责。
