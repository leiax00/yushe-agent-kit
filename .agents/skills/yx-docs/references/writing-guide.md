# 写作指南

各类文档的通用写作规范与模板。模块文档另有专属模板（见 module-docs.md），与其冲突时以专属模板为准。

## 通用原则

1. **受众先行**：动笔前先确定写给谁（使用者/运维/产品/新成员/agent）；受众不明的内容先别写。
2. **渐进披露**：第一段给出"这是什么、何时该读"的摘要；细节往后放。标题即锚点，`##` 小节可被直接链接。
3. **结论用文字，不用截图承载**：图中结论必须文字复述；流程/结构优先 Mermaid，其次表格，最后长段落。
4. **可核实性**：涉及版本敏感行为（框架 API、插件配置）标注核实日期与依据版本；未验证的写"待验证"，不写成事实。
5. **中文为主**，技术名词、命令、代码保留英文。
6. **不复制外部内容**：引用外部资料链接到 `references/` 的索引条目，正文只写结论与出处。
7. **一行一个信息点**：每行（列表项/一句话）表达一个完整的意思即可，长度本身不是问题；MUST NOT 把多个独立内容挤进一行——多个并列主题、多个操作步骤、"名称 + 解释 + 条件"混排都拆成子列表或表格。判断标准：删掉这行的前半句，后半句是否仍独立成立——成立就说明该拆。

## 头部元信息

每篇正文文档（README 索引文件除外）开头用一行引用块声明元信息：

```markdown
# <标题>

> 受众：<使用者/维护者/产品> ｜ 范围：<覆盖什么> ｜ 最后核实：yyyy-mm-dd（按 <版本/依据>）
```

内容实质变化时更新"最后核实"；只改笔误不动。

## 各类文档模板

### usage/（使用说明书）

- `quickstart.md`：目标（10 分钟内跑起来）→ 前置条件 → 步骤（可复制的命令块）→ 预期结果 → 下一步去哪。
- `configuration.md`：配置项表（项/类型/默认值/说明/是否必填），按作用分组；配置变更的影响与风险随条目注明。
- `troubleshooting.md`：症状 → 原因 → 处置，每条一个 `##` 小节；症状写用户实际看到的现象，不写内部错误码反推。

### product/（产品文档）

- `definition.md`：产品定位、目标用户与场景、功能地图（功能域 → 一句话职责 → 负责服务）、明确不做什么（负面清单）。
- 功能说明类：用户故事式（谁在什么场景做什么），不写实现；功能与服务的对应关系链接 tech/ 的架构文档。
- 设计稿索引：条目 = 名称 + 链接 + 覆盖范围 + 状态（草案/定稿/已实现）；结论性内容文字复述。

### tech/（技术文档）

- `stack.md`：技术栈表（领域/选型/版本/一句话理由摘要）；完整论证链接 `.agents/notes/`。
- `architecture.md`：系统组成图（Mermaid）+ 每个组件一段（职责、依赖、部署形态）；数据流与关键链路单独成节。
- 写现状，不写历史（历史归 history/notes）；写"是什么、为什么这样"，不写操作步骤（那是 usage 的事）。

### glossary.md（术语表）

- 按词条字母/拼音排序，每条：`## <术语>`（英文标识 `identifier`）——定义一两句 + 首次出现的背景/出处链接。
- 一个词只在此定义一次；模块内部概念不进 glossary，在模块 design.md 定义后由 glossary 链接。

### standards/（标准全文）

- 标准文档按主题一文件；条目带 RFC 2119 强度（MUST/SHOULD/MAY），与本 kit 语义一致。
- 需要强制执行的标准在 `.agents/rules/` 提炼条目并链接回本文。
- 标明来源：团队自定（共识日期）/ 参考的外部规范（链接，不复制原文）。

### references/（外部引用索引）

- 每条：名称 + 链接 + 覆盖什么 + 何时该查；失效链接标注"已失效（日期）"，不静默删除或替换。

### iterations/（迭代记录）

迭代是产品级时间盒，跨服务，放根 `docs/iterations/<编号>/`（编号用团队习惯：`2026-W46`、`R12` 等）。一个迭代一个目录，结束后冻结不改：

- `plan.md`：目标（为什么做这几件事）→ 范围（功能点列表，链接 product/ 对应条目）→ 明确不做的 → 验收标准。
- `review.md`：交付结果对照计划（完成/移出/取消及原因）→ 关键数据 → 复盘发现；改进动作的制度性结论开 note（决策记录），不堆在 review 里。

分工：iteration 记"这期做了什么"，产品能力的长期事实归 product/——迭代完成时更新功能地图；服务侧不建 iteration 目录，具体变更看各服务 releases/。

### README.md（各级索引）

- 只做路由：根 README = 项目一句话 + docs/ 目录索引表（目录/文件 → 一句话 → 何时读）+ 快速上手链接；服务 README 同构。
- 索引表是唯一内容；服务 README 另加一句"本服务在产品中的定位"。
- 不放正文段落超过三行。

## 写作流程

1. 先确认类型与受众 → 找同类型既有文档沿用其结构。
2. 写完自查：新读者能否在 30 秒内判断"这篇是否该读"；agent 能否仅凭标题和小节定位信息。
3. 提交前核对：链接有效、引用路径相对化、元信息已更新。
