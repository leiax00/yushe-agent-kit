# 发版记录（releases/）

一个版本一个文件，替代单文件滚动 CHANGELOG——版本记录天然独立，目录形态避免无关变更互相冲突，且单版本可被直接链接（`docs/releases/v1.2.0.md`）。

## 文件与格式

```text
docs/releases/
├── unreleased.md     # 未发布变更的累积区，唯一活跃文件
└── v1.2.0.md         # 已定稿的版本记录，冻结不改
```

`unreleased.md` 与版本文件同格式：

```markdown
# v1.2.0（2026-11-18）

## Added
- <新能力，一句话>

## Changed
- <行为/契约变化，注明影响>

## Fixed
- <修复的问题>
```

分类沿用 Keep a Changelog：`Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security`。

## 流程

1. 交付一个可感知变化时，同一变更追加条目到 `unreleased.md`。
2. 发版时：将 `unreleased.md` 定稿为 `v<版本>.md`（填版本号和日期），重建空 `unreleased.md`。
3. 已定稿的版本文件 MUST NOT 修改；写错在下个版本更正。

## 如何构建一份版本记录

版本记录的主要来源是**交付时同步写入**的 `unreleased.md`；发版时按下述顺序汇集、校验、补全，不靠临场回忆：

1. **读 `docs/releases/unreleased.md`**——主来源。四层分工要求合入可感知变化时同步写条目，发版时它应当已基本成形。
2. **校验遗漏：`git log <上一版本标记>..HEAD`**——对照提交记录（尤其 `feat`/`fix`/带破坏性说明的提交）逐条核对是否都已体现在 unreleased；漏记的补上。上一版本标记取上一版本文件内的日期对应的 tag/提交，没有 tag 时用上一版本文件的定稿日期。
3. **核对模块演进：本期各模块 `history.md` 新增条目**——判断机制演进是否产生对外可感知影响；有则升格为版本条目，纯内部演进不进版本记录。
4. **核对决策：本期 `implemented/` 新增与更新的 note**——其中标注破坏性变更/迁移要点的，提炼进版本记录并链接 note。
5. **核对契约：`apis/` 的 spec 变更**——接口的增删改与废弃 MUST 有对应条目。
6. **定版本号**：有破坏性变更 → major（0.x 阶段可按 minor 处理并注明）；仅新能力 → minor；仅修复 → patch。
7. **定稿**：unreleased.md 重命名为 `v<版本>.md`（填日期），重建空 unreleased.md；如仓库用 tag，同步打 tag。

范围边界：一次发版覆盖该服务自上一版本以来的全部合入；monorepo 中各服务独立执行上述流程，各自定稿。

## 记录规则

1. **只记用户可感知或影响契约的变化**（新能力、行为变更、破坏性变更、依赖要求变化）；内部重构、无感知修复不记——那是 git history 的事。
2. 破坏性变更 MUST 显式标注并写迁移要点。
3. 模块机制的演进记模块 `history.md`（见 module-docs.md），不重复进版本记录；版本记录只反映对外可感知面。

## 四层分工（统一定义，他处只引用）

| 层 | 载体 | 记什么 | 何时写 |
|---|---|---|---|
| 事实 | git history | 每次改动的精确内容 | 提交即产生 |
| 版本 | docs/releases/ | 版本级、人可读的对外变化 | 交付可感知变化时 |
| 演进 | docs/modules/*/history.md | 模块机制的演进 | 模块机制实质变化时 |
| 理由 | .agents/notes/ | 决策与取舍 | 决策发生时 |
