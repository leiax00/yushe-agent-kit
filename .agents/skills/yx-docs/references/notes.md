# 决策记录（.agents/notes/）

记录**代码和常规文档装不下的"为什么"**：设计决策、被拒绝的方案、取舍理由。参考 DSH 的 Agent Notes 体系，做通用简化——无脚本门控，靠约定执行。

**定位边界**：notes 是决策记录，不是 agent 执行日志——会话过程记录是临时产物，不落库。层级分工：跨模块/架构级决策记 notes；模块内实现演进记模块 `history.md`（见 module-docs.md，小决策理由直接写在条目里，不强制开 note）。

## 与分支/快速迭代的配合

notes 的粒度是**一次变更一条记录**，与特性分支一一对应，适合比迭代更细的快速迭代节奏：

1. 开特性分支时开一条 `proposed/` note：先写清背景、方案、替代方案、验收标准，再动手实现。
2. 实现过程中随认知更新 note 内容（方案调整、新发现的约束）。
3. 合入时一次完成：note 移入 `implemented/`（事实与代码同步）；涉及模块的 `history.md` 追加一条演进；对外可感知的变化写入 `releases/unreleased.md`。
4. 分支删除，note 留存——分支是过程，note 是记忆。

一次变更 = 分支（过程）+ note（为什么）+ history（模块演进）+ unreleased（对外变化），四层各记各的。`iterations/` 目录是可选的时间盒记录，仅当团队真的做排期与回顾时使用。

## 布局与命名

路径编码两个轴：`{生命周期}/{class}/yyyy-mm-dd-主题.md`。

- **生命周期**（顶层目录，随状态移动）：
  - `proposed/` — 尚未实现的提案，评审中。
  - `implemented/` — 决策已落地。随代码演进**保持事实同步**：代码改名、移动、改关键默认值时，同一变更更新记录中的事实（只改事实，不改写决策本身）。
  - `rejected/` — 被否决的方案。仅在"其理由能防止一个有诱惑力的重复犯错"时保留，否则删除。
- **class**（子目录，开放集合，按项目需要增删）：`feature` / `architecture` / `simplification` / `bug-fix` 等功能视角分类。
- 文件名日期 = 首次提出日期（按 git history）。

## 写作规则

1. 每篇记录：背景与问题、决策与理由、放弃的替代方案、后果、需要的验证。
2. 互引用相对 Markdown 链接，MUST NOT 用裸编号——链接可机械校验且在目录间移动后仍有效。
3. **不设中心 INDEX.md**：目录树即清单；中心索引会让无关变更在同一生成文件上冲突。
4. **替代检查**：写新记录前检索既有记录，完全取代的移入对应生命周期并互相链接；部分取代的双向链接后都保持活跃。
5. `archived/`（可选）：仅存历史价值大于指引价值的落地记录，冻结不改、不作当前依据。

## 与其他载体的分工

git history 记事实，docs/releases/ 记版本对外变化，模块 history.md 记机制演进，notes 记理由——四层不重复（统一定义见 releases.md）。模块 design.md 的"关键取舍"只留结论和指向 notes 的链接。
