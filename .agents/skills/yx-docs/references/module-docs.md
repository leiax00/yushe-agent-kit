# 模块文档指南

模块是功能视角的切分，一个模块目录承载该功能块的实现原理。核心目标：**记录代码装不下的机制与取舍**，不复述代码。

## 目录与文件

```text
docs/modules/<module>/
├── README.md       # 路由，≤30 行
├── usage.md        # 使用方法：外部有消费者时才建
├── design.md       # 实现原理：核心文档，模块存在即 SHOULD 有
└── history.md      # 实现演进史：模块存在即 SHOULD 有
```

领域概念（术语、不变量、状态机）并入 design.md 的固定小节；只有概念多到淹没原理叙述时才拆 `concepts.md`。

## README.md 模板（路由）

```markdown
# <模块名>

<职责一句话>

- 主要入口：<类/接口/函数名，不写文件路径>
- 依赖领域：<模块/领域名列表>
- 文档：[实现原理](design.md) · [使用方法](usage.md)
- 最后核实：yyyy-mm-dd（按 <项目主框架版本> 核实）
```

## design.md 结构（实现原理为核心）

1. **概述**：解决什么问题，边界在哪。
2. **机制**：核心流程怎么运转；数据流/状态流转用文字或 Mermaid，不用截图承载关键信息。
3. **关键取舍**：做了什么选择、放弃了什么、为什么；理由链指向 `.agents/notes/` 的对应记录，不在此重复长篇论证。
4. **领域概念**：术语表、不变量、状态机（简小时一节带过）。
5. **已知边界与坑**：并发约束、性能特征、易错点。

## history.md 模板（实现演进史）

记录**模块机制的演进**，不是发版清单（那是服务级 docs/releases/ 的事），也不是决策论证（那是 notes 的事）——它是模块粒度的"何时、变了什么、一句为什么"：

```markdown
# 实现演进

- 2026-11-18 引入状态机替代散落的 if/else 收敛订单状态流转（背景见 notes/<链接>）
- 2026-09-02 库存扣减改为乐观锁，悲观锁在高并发下死锁频发
```

规则：

1. 机制发生实质变化（换了做法、加了关键约束、拆了结构）时，同一变更追加一条；纯字段增删、typo 不记。
2. 每条一行：日期 + 变化 + 一句话理由；理由需要展开的链接到 `.agents/notes/`，模块内的小决策理由写在条目里即可，不必都开 note。
3. 只追加不修改；写错了下一条更正，不改历史条目。

## 写作约束

- 路径引用控制在"主要入口 + 依赖领域"粒度：写类名、接口名、模块名；MUST NOT 维护文件路径映射表——git history 是路径事实的权威，路径级映射是维护地狱。
- 引用代码用名称（`OrderAppService`）而非路径；读者用 IDE/搜索定位。
- 修改模块行为后，同一变更中同步更新 design.md 的机制描述；只改事实（名称、结构），不改写历史决策。
- 中文为主，技术名词保留英文；表格优于长段落。
