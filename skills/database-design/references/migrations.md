# 可演进迁移

沿用 Flyway/Liquibase/Alembic/Prisma 等现有工具和编号规则；已部署迁移不改写历史，新增前向修复。不要让 ORM 自动同步作为正式环境唯一迁移机制。

发布前检查：数据库版本、表大小、锁影响、备份恢复能力、应用兼容范围、长事务和迁移失败后的状态。在线建索引等能力需按产品/版本核实，不能只因语法支持就承诺无阻塞。

常用扩展—迁移—收缩顺序：先增加兼容字段/表→发布可兼容新旧结构的应用→分批回填并核对→切换读取→观察→后续发布删除旧结构。字段重命名、类型收窄、NOT NULL、唯一约束须评估旧数据和滚动发布窗口。

回填使用稳定主键范围、检查点和有限批次，设计可恢复与幂等语义；不能只使用 offset 漫扫大表。并发写入期间避免回填覆盖新值，定义双写/捕获变更和核对方案。

区分应用回滚、结构回滚和数据恢复。破坏性 DDL 不一定可逆，down 脚本不能代替备份。清楚记录迁移失败时是可重跑、需修复状态还是需前向补救。

在兼容数据库验证空库安装、已有数据升级、重复/脏数据、失败恢复、新旧应用兼容及关键查询计划。只生成脚本时报告未执行，而非迁移成功。
