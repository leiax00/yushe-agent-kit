# 通用后端架构原则

## 模块和依赖

优先按业务能力划分模块，如订单、库存、支付；模块内部再按职责分层。以一条业务用例确认依赖方向，避免只按 controller/service/mapper 建立全项目大目录。

简单 CRUD 使用接口层→应用服务→持久化适配器即可。只有复杂业务规则、状态机或多个基础设施实现需要隔离时，引入 domain 和 ports。不要为每张表机械创建聚合，也不要强制拆成微服务或多个构建模块。

领域模型不依赖 Web、数据库或远程 SDK。应用层编排用例、权限上下文和事务；基础设施实现持久化与外部服务端口。跨边界查询模型遵循所属语言的公开契约与数据所有权规则。

## 对象和共享代码

请求/响应 DTO 表示外部契约，领域对象维护业务不变量，持久化对象表达存储结构。简单模块可减少内部转换；不可因此把数据库实体作为公共请求绑定对象。DTO 的复用以契约相同且生命周期相同为条件，不因字段相似而共用。

共享模块只容纳稳定、无业务方向依赖的基础能力。避免 common/utils 逐渐成为互相依赖的业务中心。跨服务共享契约应独立版本化，不能共享 ORM 实体替代接口。

## 一致性和失败

用数据库约束兜底唯一性，用条件更新、版本号或锁明确并发策略。先检查再写入无法单独防止竞态。

本地事务只保护同一事务资源内的操作。数据库事务无法回滚已发出的 HTTP 请求。需要可靠事件交付时评估事务 outbox、重试和消费者去重；不要把“提交后发送一次”描述成可靠投递。

远程调用定义超时、失败语义和重试预算。仅对可安全重试的操作重试，避免多层重试放大流量；有副作用的调用需幂等协议。缓存说明数据来源、失效策略和可接受陈旧时间，不承担最终唯一性约束。

## 复杂度与验证

从一个实际用例和一个失败用例开始，确认权限校验、业务校验、持久化和返回值的归属。日志记录关联标识和可操作信息，不输出凭据或完整敏感对象。验证优先覆盖业务不变量、权限、边界、事务和并发，避免只测试框架委托方法。

## 模块公开面与内部实现

对采用模块化架构的新模块，区分稳定公开契约与内部实现；各语言用合适的导出机制保护边界，具体命名由语言指南规定。跨模块只通过公开面交互，应用用例按功能聚合，不建立全局万能 DTO/常量目录。
