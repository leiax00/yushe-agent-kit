# 可读性与简洁设计（所有语言）

## 目标与原则

最终代码应让维护者从名称、模块和用例流程读懂业务，保持简单、高内聚、低耦合。以 KISS（保持简单）、YAGNI（没有当前需求就不实现）和《代码整洁之道》的可读性理念作为设计方向；不把个人阈值伪装成书籍逐字规定。

MUST 实现当前已明确的需求和必要正确性，不为猜测中的扩展生成空接口、通用框架、可插拔工厂、抽象基类或备用分支。KISS/YAGNI 不意味着省略认证、输入验证、事务/并发处理和必要失败语义。

本文件是跨语言原则；排版、命名和参数数量等编码细则由各语言指南（如 Java 编码基线）定义，持久化与架构边界由对应专题文档负责。

## 命名与函数

- 名称表达业务意图和单位，避免 data、info、process、handle 等无上下文万能名字；少量上下文明确的 Handler 命名按现有用例规则保持一致。
- 一个方法处理一个清楚的任务，尽量保持同一抽象层次：顶层读起来是业务步骤，底层负责具体转换/IO。
- 用 guard clause 减少嵌套，分支结构遵循语言与团队编码基线；避免嵌套三元、过长布尔表达式和难追踪的超长链式调用。具名条件只有能解释业务含义时才抽取。
- 纯查询不隐藏写入或远程副作用；方法名与返回值体现操作语义。异常和失败信息有业务含义，不吞异常后返回虚假成功。
- 不用固定行数逼出大量跳转方法；拆分后应减少理解成本，而不是把连续简单逻辑切碎。
- 注释解释业务原因、边界、不可见约束和取舍，避免复述每行代码；公共契约说明语义、参数约束、失败和副作用。不要用长注释弥补模糊命名，修改行为时同步注释。

## 内聚、耦合与 DRY

类/模块中的状态与行为应围绕同一业务职责，避免巨型服务、万能 Utils 和字段大杂烩。依赖只暴露调用方需要的能力，传递必要数据，不传整个请求上下文、容器或无关聚合。

业务模型优先组合，继承需有合理替换语义；框架提供的技术基类复用仅限技术实现边界，不推广到业务继承。SOLID 用来判断职责和变化边界，不要求每个类都有接口或每个分支都有策略。

DRY 优先消除重复业务知识；两段外观相似但变化原因不同的逻辑可保留独立。看到第二处重复时先辨认语义，不急于把所有类似字段和步骤合并为复杂泛型工具。

## 按问题选模式，不按模式造问题

| 模式/手段 | 合适信号 | 不应采用的情况 |
|---|---|---|
| Strategy | 已存在多种可替换业务算法且需要独立演进 | 只有一个实现，或几个清楚稳定的简单分支 |
| Factory | 创建规则、类型选择或不变量需要集中保护 | 只给一次构造套同名静态方法 |
| Builder | 多字段有同一语义且无法合理拆分，需要命名构建 | 简单两字段值对象也生成一整套构建体系 |
| Adapter / Port | 隔离外部系统、存储和模块契约差异 | 每层机械增加一个只转发的接口 |
| State | 复杂状态转换规则分散且需要集中维护 | 少量状态用清楚的枚举行为即可表达 |
| Chain of Responsibility | 多个独立步骤确有顺序/组合变化需求 | 固定三个校验也建立可编排流水线引擎 |
| Observer / 事件 | 已发生事实需要多个独立消费者 | 立即要结果的普通调用被改成异步 |

采用模式前明确当前问题、最简单方案为何不足、增加哪些类型与复杂度，以及如何验证收益。无需另写设计文档；在任务说明中用一句话说明有实质取舍的决定即可。模式名称不是质量指标。

## 完成前自审

1. 新维护者能否从用例入口顺序读懂业务？名称是否需要额外解释？
2. 哪个类/方法承担了两个变化原因？拆分是否真的减少理解成本？
3. 是否存在仅为未来准备的接口、选项、工厂、通用父类或未使用代码？删除无当前用途内容。
4. 构建与依赖是否满足对应语言的编码基线，而非用参数袋或伪抽象绕过约束？
5. 重构有没有改变返回值、异常、事务边界或副作用顺序？用针对行为的测试证明。
6. 代码是否符合对应语言编码规范，同时保留原有模块边界？

对纯排版不补镜像测试；对行为变更覆盖关键成功、失败和边界用例。优先让实现与测试都能解释业务，避免测试内部方法次数来锁死合理重构。
